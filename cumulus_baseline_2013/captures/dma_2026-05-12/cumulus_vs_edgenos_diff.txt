ROOT CAUSE (4 fixes for EdgeNOS):

1. CMIC_ENDIAN_SEL must be 0x05050505, NOT 0x04000004/0x04040404.
   Each byte has bit 0 = byte-swap-enable for one of four endian
   domains (PIO, DMA_PACKET, DMA_OTHER, MSI). All four must be set
   on a big-endian PPC host. With only bit 2 set (our value), the
   chip reads DCB bytes in reversed order, finds no valid descriptor,
   and hangs the DMA channel.

2. PCIE_EP_AXI_CONFIG (0x2104) MUST NOT be zeroed. Cumulus has 0x58
   there. Our bde_open() was explicitly zeroing it via PCI config
   write — that broke the outbound AXI bridge.

3. OARR_1, OARR_2 must remain 0 (disabled). Only OARR_0 (with its
   firmware default of 0xf8 / upper 0x80) is in use on Cumulus.
   Our previous session enabled OARR_1/2 hoping it would help —
   it didn't, and is the wrong thing to do.

4. PAXB_ENDIAN (0x2030) should be 0xf3, not 0xf2 (bit 0 swap-enable
   for PAXB outbound).

Fixed in EdgeNOS commit 7fbfb7d's bde_interface.c successor (this
session): bde_set_dma_endianness() now writes 0x05050505 to
CMIC_ENDIAN_SEL and 0xf3 to PAXB_ENDIAN; bde_open() no longer
touches PCIE_EP_AXI_CONFIG or OARR_*.

Post-ENDIAN-fix session continuation 2026-05-12:

ENDIAN_SEL=0x05050505 fix applied + verified — TX DMA poll TIMEOUT is now 0.
tcpdump on swp2 shows ARP requests broadcasting correctly with the right MAC:
   80:a2:35:81:ca:b0 > ff:ff:ff:ff:ff:ff, ARP Request who-has 10.101.101.9 tell 10.101.101.10

But ping still fails. New blocker found:

  bmd_rx_start failed: -19 (CDK_E_IO)
  RX DMA init failed - RX path disabled

Drilling into the call chain:
  bcm56840_a0_bmd_rx_start
    → bmd_xgs_dma_rx_start  (returns CDK_E_NONE)
    → rv = _cpu_port_enable_set(unit, 1)
    → returns rv

  _cpu_port_enable_set:
    ioerr += READ_EPC_LINK_BMAPm(unit, 0, &epc_link);
    ... set CMIC_PORT bit ...
    ioerr += WRITE_EPC_LINK_BMAPm(unit, 0, epc_link);
    return ioerr ? CDK_E_IO : CDK_E_NONE;

So a SCHAN-mediated read or write of EPC_LINK_BMAPm is failing.  Without
CMIC_PORT (CPU port) in EPC_LINK_BMAP, the egress pipeline doesn't
forward received frames to the CPU, so ARP replies coming back from
the Nexus would be silently dropped at the chip's egress stage instead
of being DMA'd into our RX ring.

This is a fifth register-level fix to discover for next session.
Specifically: capture what EPC_LINK_BMAP looks like during working
Cumulus operation (expected to have CMIC_PORT bit set) and figure out
why our SCHAN read/write to EPC_LINK_BMAPm fails when other SCHAN ops
(used by bmd_init successfully) work. Likely culprits:

  - EPC_LINK_BMAPm is a *memory* (m-suffix) accessed via a different
    SCHAN opcode than registers — chip may need TBL_R/TBL_W rather
    than MEM_R/MEM_W on this generation.
  - The memory write path needs a specific block/port encoding our
    CDK macro doesn't supply.
  - Memory write on this chip needs MMU credit / EPC unlock first
    that bmd_init doesn't do.
