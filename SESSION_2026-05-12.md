# Session 2026-05-12 — First end-to-end install of EdgeNOS on hardware

Day-long session that pushed EdgeNOS from "builds locally" to "running on
the chassis with all 52 ports up as Linux netdevs". Built the ONIE
installer, captured the live ONIE userspace and U-Boot env, fixed five
build-script bugs, installed end-to-end, debugged the userspace daemon,
and finally got the DMA pool allocating so TX works.

Not yet done: ping to the Nexus peer. RX punt is the next target.

## 3. Install via Option A (SSH stream to /tmp + onie-nos-install)

Pushed the 140 MB `.bin` over SSH while the chassis was in ONIE install
mode at `10.1.1.222`:

```sh
ssh root@10.1.1.222 'cat > /tmp/installer.bin && chmod +x /tmp/installer.bin && onie-nos-install /tmp/installer.bin' \
  < output/images/edgenos-as5610-52x.bin
```

Install ran clean — partition, mke2fs, dd FIT to sda5, dd squashfs to
sda6, fw_setenv. ONIE printed `Failure: Unable to install image` because
its `exec_installer` line 469 calls `reboot` without full path
(`/sbin` not in ONIE's $PATH — documented ONIE_ISSUES.md §8/§10). Our
`install.sh` had already called `/sbin/reboot` before that; install
succeeded despite the spurious error.

Chassis came back at `10.1.1.212` (sticky DHCP lease) running
**EdgeNOS kernel 5.10.224**, hostname `edgenos`, login `root:as5610`.

## 5. Cross-compiling edged on the host (one-shot)

After install, rather than rebuilding the full image we cross-compiled
**just** the `edged` binary in a disposable docker container and scp'd
it onto the running system. Key lessons:

- **`scripts/build-sdk.sh` is broken** — it tries to build BMD without
  the required `BMD_SYS_USLEEP` / `BMD_SYS_DMA_ALLOC_COHERENT` /
  `BMD_SYS_DMA_FREE_COHERENT` defines. Those macros configure how BMD
  reaches into the application's libc and DMA pool.
- **`asic/mdk-init/Makefile` is the canonical SDK build path** — it
  defines those macros and produces all 16 static libs (CDK × 7, BMD × 4,
  PHY × 4, libbde × 1) under `output/sdk/`.
- gcc-12 (Debian bookworm) is too strict for OpenMDK source —
  `-Wimplicit-function-declaration` is an error. **Use Debian bullseye
  (gcc-10) for OpenMDK builds.**
- Need `libc6-dev-powerpc-cross` + `linux-libc-dev-powerpc-cross` for
  32-bit PowerPC userspace cross-compilation (not just the 64-bit ppc64
  multilib that comes with the cross-gcc package by default).

The final `edged` binary is **18 MB static**, all SDK libs linked in.

## 6. DMA pool diagnosis — the big puzzle

After `edged` deployed, the log filled with:

```
BDE: No DMA pool available
TX: DMA alloc failed for swpN (70 bytes)
```

Kernel dmesg revealed:

```
linux-kernel-bde 0001:01:00.0: DMA alloc 64 MB failed, halving
linux-kernel-bde 0001:01:00.0: DMA alloc 32 MB failed, halving
linux-kernel-bde 0001:01:00.0: DMA alloc 16 MB failed, halving
linux-kernel-bde 0001:01:00.0: DMA alloc 8 MB failed, halving
linux-kernel-bde 0001:01:00.0: Failed to allocate DMA pool at any size
```

`/proc/buddyinfo` showed plenty of free 4 MB chunks (`Node 0, zone Normal
... 174` at order 10). Why was even 8 MB failing?

### Root cause

**PPC32 buddy allocator has `MAX_ORDER=11`.** That means the largest
contiguous allocation the page allocator can return is `2^(MAX_ORDER-1)
* PAGE_SIZE = 2^10 * 4 KB = 4 MB`. Anything bigger needs CMA.

And CMA is broken on this kernel — `/proc/meminfo` reports
`CmaTotal: 0 kB` and `CmaFree: 0 kB` despite `CONFIG_CMA=y`,
`CONFIG_DMA_CMA=y`, `CONFIG_CMA_SIZE_MBYTES=32`, and `cma=32M` on the
kernel cmdline. Kernel boot log shows `0K cma-reserved`. This is a known
PPC32 + FSL P2020 issue where CMA silently fails to reserve at boot.

Our BDE halving loop bottomed out at 8 MB — **always above the 4 MB
buddy ceiling, so every attempt was guaranteed to fail**.

### Fix

Drop the halving floor from 8 MB → 1 MB in
`asic/bde/linux-kernel-bde.c:309-329`:

```c
unsigned int try_mb = dma_size;
while (try_mb >= 1) {
    bdev->dma_size = try_mb * 1024 * 1024;
    bdev->dma_virt = dma_alloc_coherent(...);
    if (bdev->dma_virt) { ... break; }
    try_mb /= 2;
}
```

After redeploying the patched `linux-kernel-bde.ko`, the first 4 MB
attempt succeeded:

```
BDE: DMA pool 4 MB at phys 0x7400000 mapped at 0xb7b34000
```

For ping/ARP-level traffic, 4 MB is plenty (16 RX buffers × 2 KB + per-TX
DMA-coherent allocs).

### Follow-up

Real fix is to make CMA work on PPC32 + P2020 — likely needs a
`reserved-memory` node in the DTS and earlier boot init. Or move BDE to
a built-in / initramfs init so it gets the 64 MB chunk before fragmentation.

## 9. Where TX DMA actually fails (this session's new finding)

After the xgsd_dma migration was pulled into pkgsrc and rebuilt,
`bmd_tx` returns `CDK_E_TIMEOUT (-9)` from
`bmd_xgsd_dma_chan_poll`. The DMA STAT register's `CHAIN_DONE` bit for
chan 0 (TX) never sets.

Per `cumulus_baseline_2013/CMIC_SCHAN_DMA_DEEP_DIVE.md §3` and the
May 9 finding:

> Some registers that *appear* to be at fixed MMIO addresses are
> actually **SCHAN-mediated** — i.e., the MMIO address you see in
> documentation is a "shadow" that only takes effect when you go through
> the proper SCHAN protocol. Writing them via direct `*reg = value`
> either reads back stale or silently fails.

May 9 isolated this concretely:

> Direct probe writes to ANY CMICm DMA CTRL register don't stick
> (write 0xDEADBE5A reads back as original) — but writes via switchd's
> BMD path do change state.

So **either**:
- our CDK_DEV_WRITE32 path for CMIC_CMC_DMA_CTRLr isn't actually
  reaching the chip (sub-window 7 remap mishap?), OR
- it IS reaching the register but the chip's DMA engine never reads
  the descriptor (OARR / endianness / DCB format mismatch on the host
  memory side), OR
- the register write succeeds but the DMA engine needs an additional
  start trigger (`DMA_HALT_ADDR` write, IRQ enable, etc.) we're missing.

Concrete diagnostic plan for next session:

1. **Capture the live BAR0 DMA region after Cumulus 2.5.1 successfully
   transmits a packet.** Specifically:
   - `CMIC_CMC0_DMA_CTRL[0..3]` (BAR0+0x31140..0x3114c)
   - `CMIC_CMC0_DMA_DESC[0..3]` (BAR0+0x31158..0x31164)
   - `CMIC_CMC0_DMA_STAT[0..3]` (BAR0+0x31150..0x3115c)
   - PAXB OARR_2 (PCI config 0x2D60) + OARR_2_UPPER (0x2D64)
   - IMAP0_0..7 (BAR0+0x2C00..0x2C1C) — what sub-window mapping is
     active when Cumulus transmits?
2. **Diff against our state under EdgeNOS** when a TX attempt is in
   flight (just before the timeout fires).
3. **Specific register-write test:** under EdgeNOS, write 0xDEADBE5A
   to `CMIC_CMC_DMA_CTRL[0]` via `CDK_DEV_WRITE32` (our edged's path)
   AND via raw `BDE_IOC_REG_WRITE` ioctl. Read both back. May 9 saw
   the BMD path change state but a "direct" path didn't — which paths
   exactly? Verify and narrow.
4. **If sub-window 7 is the culprit:** pre-map sub-window 1 (or any
   non-7) to AXI 0x18031000 statically at probe time, so DMA-CTRL
   accesses never need a dynamic remap. The "every access remaps
   sub-win 7" log spam from a244e3f suggests the cache is invalid;
   making the DMA window static would also stop the noise.

Everything below this section about Cumulus PCS lock or retimer CDR
being broken should be considered superseded by "hardware is fine,
Cumulus 2.5.1 demonstrated it, look at our chip-control software."
